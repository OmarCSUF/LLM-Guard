# Changes from the original workspace

This repository is the completed LLM-Guard study code, restructured for publication. The
experiments were not re-run; the stored results in `results/` are the originals and every
number in the paper regenerates from them unchanged. The git history of the original
workspace (60 commits, up to the frozen commit `dc90a9e2`) is preserved, so the commit hashes
recorded in every `run_info` block and in `frozen.json` resolve here.

Behaviour was verified after the restructure by re-scoring 80 final-test prompts with the
shipped Layer-1 checkpoint (identical scores and decisions to the stored predictions), by
regenerating every `analysis/` file from the stored predictions (byte-identical), and by the
test suite (`make test`). The timeline of the final study and the reconstructed runner are in
`REPRODUCIBILITY.md`, section 8; what cannot be reproduced and the manuscript discrepancies
are in its sections 5 and 6.

### Environment override: `LLMGUARD_JUDGE_MODEL`

Set it to a local directory or another hub id to load the judge/guard model
from somewhere other than `Qwen/Qwen2.5-3B-Instruct`:

```
LLMGUARD_JUDGE_MODEL=/home/OmarLaptop/hf_models/Qwen2.5-3B-Instruct \
  PYTHONPATH=src python scripts/run_evaluation.py ...
```

Rules, implemented in `llmguard.utils.config_loader.judge_model(section)`:

- It is read at `from_config` time by **both** `LLMJudge.from_config`
  (Layer 2) and `GuardLLM.from_config` / `Layer3Mitigator._shared_weights`
  (Layer 3), so the sharing check compares the same string on both sides and
  Layer 3 still reuses the Layer-2 weights.
- With the override, the pinned `revision` is **not** applied: it belongs to
  the configured hub id, a local directory has none, and another hub id has
  a different one. `from_pretrained` is then called exactly as the recorded
  runs called it with the local directory.
- An unset or blank variable changes nothing.
- It takes precedence over a `model_name` a script wrote into the config dict
  (`scripts/tune_judge.py --judge-model`, `scripts/final_eval/run_judge_only.py
  --judge-model`), because those scripts call `LLMJudge.from_config` after
  editing the dict. Unset the variable when using those flags.

### Code changes

#### `src/llmguard/utils/config_loader.py`

Before: ten lines; `load_config(path="config/config.yaml")` opened the path
relative to the cwd and raised `FileNotFoundError` otherwise.

After:

- `load_config(path)`: unchanged for an explicit path. With the default path,
  when `config/config.yaml` does not exist from the cwd, it falls back to
  `<repo root>/config/config.yaml` (`REPO_ROOT = Path(__file__).resolve().parents[3]`).
  The same `FileNotFoundError` is raised when neither exists.
  `scripts/framing_diagnostic.py` passes the default string explicitly and
  gets the same fallback (same string, same rule).
- `repo_path(path)`: returns a path unchanged when it is absolute or exists
  from the cwd; otherwise the copy under the repo root when that exists;
  otherwise the path as given (so the caller's own error names it).
- `judge_model(section)`: `(model_name, revision)` for `layer2.judge` or
  `layer3.guard_llm`, with the `LLMGUARD_JUDGE_MODEL` rule above. A missing
  or empty `revision` key gives `None`.
- `hub_kwargs(revision)`: `{"revision": revision}` when set, else `{}`.
- Constants `DEFAULT_CONFIG_PATH`, `REPO_ROOT`, `JUDGE_MODEL_ENV`.

### Code changes

#### `scripts/fetch_datasets.py`

* New `--revision-manifest PATH`: pins every repository named in the manifest
  to its recorded revision. Accepts the `sources` block written by the fetch
  scripts or the `source_revisions` block of `data/benchmarks_final/manifest.json`
  / `results/development/pool_metadata.json`. The tree listing is fetched at
  `/api/datasets/<repo>/tree/<sha>` and files from `/datasets/<repo>/resolve/<sha>/<path>`.
  For every file with a recorded digest the Hub's listed digest (and algorithm)
  at that revision must equal the recorded one, otherwise the source fails with
  `DIGEST MISMATCH ...` before anything is downloaded; the existing content
  verification against the Hub digest then guarantees the downloaded bytes equal
  the recorded ones. A pinned manifest entry gets an extra `"pinned": true`.
* New `--revision REPO=SHA` (repeatable; `REPO` is a Hub id or a source name):
  pins one repository, overriding the manifest, with no digests to enforce.
* New helpers `add_pin_arguments(parser)`, `load_revision_pins(manifest_path,
  overrides, sources=None)` and `_check_pinned_digest(...)`;
  `fetch_source(name, out_dir, token, pins=None)` gained the optional `pins`
  argument.
* Logging only: a pinned repository logs its revision; with a pin table in use,
  a repository absent from it logs a warning that its current revision is fetched.
* Default behaviour (no flag): identical. `pins` is `None`/`{}`, the current
  revision is queried from `/api/datasets/<repo>` as before, and the manifest
  entry has the same keys as before. Token handling (`HF_TOKEN`, then
  `huggingface_hub.get_token()`; sent only to the `HF_ENDPOINT` host; never
  printed) is unchanged.

#### `scripts/final_eval/fetch_final_sources.py`

* Same two flags, added through `fd.add_pin_arguments`; pins are built with
  `fd.load_revision_pins(..., FINAL_SOURCES)` so source names such as `phtest`
  resolve, and passed to `fd.fetch_source`. Default behaviour identical.

#### `scripts/final_eval/build_final_test.py`

* New `--require-tokenizer`: if the `roberta-base` tokenizer is not in the local
  Hugging Face cache, exit with an explicit error instead of skipping the
  `over_512_tokens` step. Default off = the recorded behaviour (skip), but the
  skip is now logged as a WARNING that names the consequence (the output hash
  differs from the recorded build) instead of being silent.
* New `--backbone-revision SHA`: passed as `revision=` to
  `AutoTokenizer.from_pretrained(..., local_files_only=True)` so a specific cached
  snapshot is used. When not given, the keyword is not passed at all, so the
  call is byte-for-byte the old one.
* `count_long(records, tokenizer_name, limit, require=False, revision=None)` and
  `build(..., require_tokenizer=False, backbone_revision=None)` gained keyword
  arguments with defaults equal to the old behaviour; docstrings added.
* Logging only: the number of flagged prompts per source, and at the end the
  output sha256 next to the recorded `39425a51...`.
* The screening logic (rules 1 to 4, seeds, thresholds, source precedence, DNA
  split) is untouched.

### 3. The CUDA note

The recorded torch wheel is `2.14.0+cu130`, the CUDA 13.0 build from PyTorch's
own index. `pip install torch==2.14.0` from PyPI may give a different CUDA build
(or a CPU build), so install torch first and from the index that matches the
machine:

    pip install torch==2.14.0 --index-url https://download.pytorch.org/whl/cu130
    pip install -r requirements.txt

The `cu130` index is what this machine used; another driver or platform needs
another index (`cu128`, `cpu`, ...). The `nvidia-*` entries in
`requirements-lock.txt` are the CUDA runtime wheels that came with it. The
Layer-1 classifier and the fusion stacker give the same scores on CPU; the
4-bit judge and Guard-LLM (bitsandbytes NF4) need a CUDA device.
